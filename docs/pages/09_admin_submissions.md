# 페이지 명세: 관리자 제보 승인 관리 (`/admin/submissions`)

> 경로: `/admin/submissions`  
> 상태: [MVP] 1차 구현 대상  
> 대상 플랫폼: 데스크톱 웹  
> 레이아웃: 관리자 셸 (사이드바 + 3개 탭 뷰 + 검토 상세 패널/모달)

---

## 1. 페이지 목적 및 접근 권한

### 1.1 페이지 목적
- 일반 사용자(회원 및 비회원)가 제출한 신규 장소 제보와 기존 장소 정보 수정 제보를 관리자가 검토하여 승인(공식 DB 반영) 또는 반려 처리한다.
- 정보 수정 제보의 경우 기존 등록 데이터와 제안된 수정 데이터를 직관적으로 비교(Diff)할 수 있는 환경을 제공한다.

### 1.2 접근 권한
- **관리자 전용 (`profiles.role = 'admin'`)**
- 관리자 외 접근 불가.

---

## 2. UI 구성과 사용자 동작

### 2.1 상단 탭 내비게이션 (SITEMAP.md §9)
- 단일 화면 내에서 3개의 탭으로 구분:
  1. **[신규 장소 탭]**: `type = 'new_place'`이며 미처리 상태(`received`, `in_review`)인 제보 목록.
  2. **[정보 수정 탭]**: `type = 'correction'`이며 미처리 상태인 제보 목록.
  3. **[처리 완료 탭]**: 이미 승인(`approved`) 또는 반려(`rejected`)된 제보 히스토리 목록.

### 2.2 신규 장소 탭 UI 및 동작
- **목록 테이블**:
  - 컬럼: 접수 일시, 제보 장소명, 카테고리, 주소, 제보자(회원 닉네임 또는 '비회원'), 액션([검토 및 승인]).
- **검토 상세 모달**:
  - 제안된 데이터 확인: 장소명, 주소, 지도 핀 위치, 카테고리, 요일별 영업시간, 전화번호, 메모 등.
  - **중복 장소 확인 기능**: 기존 등록 장소 중 유사한 위치/이름을 가진 장소가 있는지 자동 매칭해 표시.
  - **액션**:
    - **[승인하여 공개 장소로 등록]**: 확인 팝업 후 승인 처리 (`places` 신규 행 생성).
    - **[반려하기]**: 클릭 시 반려 사유 입력 다이얼로그 표시.

### 2.3 정보 수정 탭 UI 및 동작
- **목록 테이블**:
  - 컬럼: 접수 일시, 대상 장소명, 변경 제안 요약(예: "영업시간 단축", "폐업 신고"), 제보자, 액션([검토하기]).
- **검토 상세 모달 (Diff 화면)**:
  - **기존 공식 데이터 vs 제안된 수정 데이터 좌우 비교(Side-by-Side Diff)**:
    - 변경된 항목은 노란색/연파란색 배경으로 강조 표시.
    - 예: 기존 영업시간 `18:00~03:00` → 제안된 영업시간 `18:00~01:00`.
  - 제보자가 작성한 수정 근거 메모 확인.
  - **액션**:
    - **[수정 사항 승인 및 반영]**: 공식 장소 데이터에 제안된 필드만 원자적으로 갱신.
    - **[반려하기]**: 반려 사유 입력 다이얼로그 표시.

### 2.4 반려 사유 입력 다이얼로그 (공통)
- 제보 반려 시 **반려 사유(`rejection_reason`) 입력은 필수** (공백 불허, DB.md §3.7).
- 자주 쓰는 템플릿 제공:
  - *"현장 확인 결과 정상 영업 중인 것으로 확인되었습니다."*
  - *"제공해주신 정보가 불충분하여 확인이 어렵습니다."*
  - *"이미 동일한 정보가 등록되어 있습니다."*
- [반려 확정] 클릭 시 상태가 `rejected`로 변경되고 회원은 본인 마이페이지(추후)에서 사유 확인 가능.

### 2.5 처리 완료 탭
- 처리 완료된 제보 내역 조회:
  - 컬럼: 처리 일시, 유형(신규/수정), 대상 장소명, 처리 결과(승인 뱃지 / 반려 뱃지), 검토 관리자 닉네임, 반려 사유(반려 시).

## 3. DB 연동 및 트랜잭션

### 3.1 호출 API
- `GET /api/admin/submissions?type=new_place&status=received`
- `GET /api/admin/submissions?type=correction&status=received`
- `POST /api/admin/submissions/:id/approve` (승인 트랜잭션)
- `POST /api/admin/submissions/:id/reject` (반려 트랜잭션)

### 3.2 승인 트랜잭션 불변조건 (DB.md §8.2, §8.3)
1. **신규 장소 승인**:
   - `submissions` 행 잠금(`FOR UPDATE`).
   - `places` 테이블에 레코드 INSERT.
   - `place_regular_day_status`, `place_regular_intervals`, `place_tags` INSERT.
   - `place_change_history`에 생성 스냅샷 기록.
   - `submissions.status = 'approved'`, `reviewed_by = auth.uid()`, `reviewed_at = now()`, `result_place_id = places.id`.
   - 단일 트랜잭션으로 커밋.
2. **정보 수정 승인**:
   - 대상 장소 행 잠금.
   - 변경 전 스냅샷 확보.
   - **제보가 제안한 필드만 선별적으로 UPDATE**하고 다른 필드는 보존.
   - `submissions.status = 'approved'`, `reviewed_by = auth.uid()`, `reviewed_at = now()`.
   - `place_change_history`에 변경 전후 스냅샷 기록.
   - **주의**: 정보가 수정되었다고 해서 `places.last_verified_at`을 자동으로 갱신하거나 `verified`로 바꾸지 않음 (실확인과 분리 원칙).
   - 대상 장소의 미해결 제보가 없으면 '정보 수정 제보 접수' 경고 자동 해제.

## 4. 예외 상태 (Error States)

### 4.1 반려 사유 공백
- 반려 사유를 입력하지 않고 제출 시도 시:
  - `"반려 사유를 반드시 입력해주세요. (공백 불가)"` 에러 표시 및 차단.

### 4.2 중복 승인/동시성 충돌
- 다른 관리자가 이미 승인 또는 반려 처리한 제보를 다시 처리하려 할 때:
  - `"이미 다른 관리자에 의해 처리가 완료된 제보입니다."` 안내 및 목록 갱신.

---

## 5. 완료 조건 (Acceptance Criteria)

1. [ ] 신규 장소 탭, 정보 수정 탭, 처리 완료 탭이 분리되어 정확한 상태의 제보가 표시된다.
2. [ ] 신규 제보 검토 시 제안 정보 및 중복 후보 확인이 가능하다.
3. [ ] 정보 수정 제보 검토 시 기존 데이터와 제안 데이터의 차이점(Diff)이 명확히 표시된다.
4. [ ] 승인 시 단일 트랜잭션으로 공식 장소 및 영업시간에 안전하게 반영된다.
5. [ ] 반려 시 사유 입력이 강제되며, 사유 없이 반려할 수 없다.
6. [ ] 승인/반려 완료 후 대상 장소의 미해결 주의 표시가 적절히 해제된다.
