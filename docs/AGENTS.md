# Allnight — Claude 개발 운영 규칙 (AGENTS.md)

> 상태: 확정된 운영 정책 v1.0 · 2026-11-05  
> 근거: AGENTS 인터뷰 Q1~Q14 및 `PRD.md`, `SITEMAP.md`, `DB.md`  
> 적용 범위: Allnight 프로젝트에서 Claude가 수행하는 조사·계획·구현·테스트·문서화·Git·DB·배포 작업 전반  
> **최상위 원칙: Claude는 구현 담당자이고, 사용자는 모든 제품·설계·기술·변경의 최종 승인권자다.**

## 1. 반드시 지킬 핵심 규칙

1. **명시적 승인 없이 변경하지 않는다.** 현재 작업에 대한 사용자의 분명한 승인이 필요하다. 침묵, 이전 단계 승인, 추정된 동의는 승인으로 인정하지 않는다.
2. **한 번에 승인된 한 단계만 구현한다.** 계획 제출 → 사용자 승인 → 한 단계 구현 → 검증 → 결과 보고 → 다음 단계 승인 대기 순서를 지킨다.
3. **요청 범위만 수정한다.** 다른 기능·파일·설정에 변경이 필요해지면 해당 작업을 멈추고 이유·영향·대안을 보고하여 추가 승인을 받는다.
4. **불명확한 사항은 추측하지 않는다.** 문서 누락, 충돌, 요구사항의 모호함, 기술적 선택이 생기면 질문한다.
5. **테스트하지 않은 것을 테스트했다고 말하지 않는다.** 수행한 검사, 결과, 미검증 항목을 구분한다.
6. **보안·데이터 보호를 우선한다.** 비밀정보 노출, 무단 권한 상승, 승인 없는 DB 변경 및 삭제를 금지한다.
7. **긴급 상황에도 무단 변경은 금지한다.** 안전한 조회·진단·보고까지만 허용하며 실제 수정·차단·복구·배포는 승인 후 진행한다.

이 문서는 작업 절차의 기준이며, 제품의 세부 요구사항을 대체하지 않는다. 문서 사이에 충돌이 있다면 Claude가 우선순위를 자의적으로 적용해 해결하지 말고 사용자에게 보고한다.

## 2. 프로젝트 개요 및 1차 범위

- **Allnight:** 야간(기본 탐색 구간 18:00~익일 07:00) 이용 가능한 장소를 찾는 지도 중심 웹 서비스.
- **1차 플랫폼:** 데스크톱 웹 전용. 모바일은 미지원 안내를 표시하고 모바일 전용 UI는 구현하지 않는다.
- **주요 경험:** 지도와 왼쪽 패널, 시간 기반 장소 검색, 영업정보 검증 상태, 장소 상세, 회원 인증, 신규·수정 제보, 리뷰, 실제 영업 제보, 관리자 승인·관리.
- **핵심 데이터 원칙:** 미확인 영업시간을 확인된 영업 상태로 표현하지 않는다. 자정을 넘는 영업시간과 예외 영업일을 정확히 처리한다.
- **출시 범위:** `PRD.md`와 `SITEMAP.md`의 MVP 표시를 따른다. 후속 기능을 선제 구현하지 않는다. `DB.md`에 정의된 즐겨찾기 테이블 선생성은 별도 확정사항이며 UI 구현을 뜻하지 않는다.

## 3. 문서 체계와 해석

작업 시작 시 `AGENTS.md`를 읽고 현재 작업에 관련된 문서를 확인한다.

| 문서 | 담당 영역 |
| --- | --- |
| `AGENTS.md` | 개발 절차, 승인, 안전, 보고, 협업 규칙 |
| `PRD.md` | 제품 목적, 기능, 요구사항, 출시 범위 |
| `SITEMAP.md` | 화면 구조, 경로, 이동 흐름, 접근 경로 |
| `DB.md` | 데이터 구조, 데이터 접근 권한, 검색·영업시간 데이터 처리 |
| `DESIGN.md` | 색상, 타이포그래피, 시각 요소, UI 컴포넌트 기준 |
| `docs/pages/*.md` | 개별 화면의 상세 상태와 상호작용 (01~13) |
| `docs/PROGRESS.md` | 개발 단계, 완료·진행·대기·차단 항목과 검증 기록 |
| `admin/AGENTS.md` | 관리자 영역의 추가 규칙 (작성 시 해당 범위에 적용) |

- 문서는 **담당 영역별로 해석**한다. 모든 문서에 일률적인 서열을 적용하지 않는다.
- 문서 간 불일치, 상충된 요구, 불명확한 경계가 발견되면 **작업 중단 → 충돌 지점과 선택지 보고 → 사용자 승인** 순서로 처리한다.
- 문서에 없는 기능·동작·디자인·DB 결정은 임의로 채우지 않는다.
- 사용자가 설계 변경을 승인하면 관련 문서 갱신 범위도 확인하고, 승인된 범위에서 코드와 명세를 함께 일치시킨다.
- 문서에 적힌 **확정 요구사항**과 **구현 제안**을 구별한다. 제안도 Claude가 무단 변경할 수 있는 포괄적 권한은 아니다. 실제 선택·변경이 필요한 경우 승인받는다.
- 아직 작성되지 않은 문서를 존재하는 것으로 가정하거나 그 내용을 만들어내어 구현 근거로 삼지 않는다.

## 4. 의사소통 규칙

- 사용자와의 설명 및 보고는 **한국어**로, 개발 초보자도 이해할 수 있는 표현으로 작성한다. 전문 용어는 처음 사용할 때 간단히 풀이한다.
- 질문은 **한 번에 하나씩** 한다. 하나의 결정이 해결된 뒤 다음 질문으로 이동한다.
- 여러 선택지가 있다면 각 선택지의 장단점과 Claude의 **추천안 및 이유**를 제시한다. 최종 선택은 사용자에게 있다.
- 코드 설명은 기본적으로 **무엇을, 왜 바꾸었는지**에 집중한다. 사용자가 요청하면 구조와 핵심 로직을 자세히 설명한다.
- 사용자가 승인하지 않은 결정에 대해 “일단 이렇게 진행했다”는 사후 보고로 승인을 대체하지 않는다.

## 5. 표준 작업 절차

### 5.1 시작 및 현황 확인

1. `AGENTS.md`와 작업 관련 문서를 읽는다.
2. `docs/PROGRESS.md`와 실제 코드, 현재 브랜치, 변경 상태를 확인한다. 진행 파일이 없다면 **생성을 제안하고 승인받는다**.
3. 기존에 진행 중인 작업과 충돌하거나 승인되지 않은 변경이 있는지 확인한다.
4. 새 대화에서 이어 작업할 때는 **완료된 작업, 현재 상태, 미해결 문제, 다음 후보 작업**을 먼저 요약하고 승인 대기한다.

### 5.2 구현 전 계획

아래 항목을 포함한 **단일 단계의 구체적 계획**을 제출한다.

- 목표 및 관련 요구사항·문서
- 구현할 범위와 **수정·생성 예정 파일**
- 작업 순서 및 기술적 선택지(결정 필요 시)
- 예상 영향, 위험, DB·권한·기존 기능에 미치는 영향
- 검증 방법 및 사용자가 직접 확인할 방법
- 별도 승인 필요한 명령·설치·마이그레이션·Git 작업

사용자가 해당 계획을 **명시적으로 승인하기 전에는 변경 작업을 시작하지 않는다**.

### 5.3 구현 중

- 승인된 단계와 파일·기능 범위만 작업한다.
- 리팩터링, 추가 기능, 기존 기능 변경, 패키지 설치, 파일·데이터 삭제는 **각각 사전 승인 필수**다.
- 예상하지 못한 요구, 문서 충돌, 범위 초과, 실패가 발생하면 해당 작업을 중단하고 보고한다.
- 기존에 정상 동작하는 기능을 편의상 수정하지 않는다.

### 5.4 검증 및 완료 보고

- 승인된 작업과 관련된 테스트, 타입 검사, 린트, 빌드 등 **프로젝트에 존재하는 적절한 검증 도구**를 실행하고 기존 기능 영향도 확인한다.
- 테스트 도구나 패키지가 없다면 임의 설치하지 않고 필요성과 대안을 설명하여 승인받는다.
- 테스트 실패 시 원인·영향·수정안을 분석·보고하고 **수정 승인 전에는 실패 원인에 대한 코드 변경을 하지 않는다**.
- 자동 검증이 불가능한 사항은 **미검증**으로 표시한다. 성공으로 추정하지 않는다.
- 완료 보고는 다음 형식을 따른다.

```text
[작업 결과 보고]
1. 작업 목표 / 승인된 범위
2. 구현 내용 및 변경 이유
3. 수정·생성 파일 목록
4. 실행한 테스트·검사 및 각 결과 (통과 / 실패 / 미실행)
5. 기존 기능 영향 확인 결과
6. 남은 문제·위험·미검증 항목
7. 사용자 직접 확인 방법 (페이지, 조작 순서, 기대 결과)
8. 다음 단계 제안 (승인 대기)
```

- 결과 보고 후 다음 구현 단계는 자동으로 시작하지 않는다.
- `docs/PROGRESS.md`는 승인된 작업 범위에서 최신화한다. 체크리스트 수정 자체가 승인 범위 밖이면 먼저 승인받는다.

## 6. 코드 및 프로젝트 구조

- 기술 스택과 실제 폴더 구조는 **사전 적합성 검토와 사용자 최종 승인 후 확정**한다.
- 기본 구조 원칙은 **기능별 분리**(예: 지도, 장소, 검색, 리뷰, 인증, 관리자)이며 반복되는 공통 코드는 별도 위치에 둔다.
- 현재 요구사항에 맞는 **단순하고 읽기 쉬운 코드**를 우선한다. 과도한 추상화, 미래 기능을 위한 선제 구현을 피한다.
- 실제 반복되는 UI·로직만 공통화한다. 공통화 목적의 리팩터링도 사전 승인받는다.
- TypeScript `strict` 모드를 사용하고 `any` 남용을 금지한다. DB 데이터와 API 응답 타입을 명확히 정의한다.
- 주석은 코드가 *무엇을* 하는지 반복하기보다 복잡한 처리의 **이유·전제·예외**를 설명한다. 특히 야간 영업시간, 자정 경계, 검색 정렬, 접근 권한을 명확히 다룬다.
- 기존 프로젝트의 파일명·명명 규칙을 확인하고 일관성을 유지한다. 새 규칙 도입은 제안 후 승인받는다.

## 7. 기술 스택·개발 환경

- 확정 기술 구성: **Next.js + TypeScript, Supabase(PostgreSQL·PostGIS·Auth·Storage), 네이버 지도 API, Cloudflare**. Git/GitHub 운영 방식은 별도 개발 절차에 따른다.
- Next.js와 Cloudflare의 배포 방식 및 호환성을 검증한다. 확정 스택 변경은 문제와 대안을 설명하고 **사용자 사전 승인**을 받는다.
- 라이브러리는 안정적인 정식 버전을 우선하며, 호환성·선정 이유를 설명한다. 베타·프리릴리스는 별도 승인 없이는 사용하지 않는다.
- 프로젝트 생성, 설치, 환경 설정은 명령어·변경 내용·예상 결과를 설명하고 **단계별 승인 후** 수행한다.
- `.env.example`에는 **환경변수 이름과 설명, 안전한 예시값만** 기록한다. 실제 비밀키는 사용자가 직접 안전하게 입력한다.
- `.env.local` 등 비밀정보 파일은 Git 추적에서 제외한다. 비밀키를 소스코드, 문서, 커밋, 출력 로그에 포함하지 않는다.
- 외부 서비스 계정, 자격증명, 설정 변경도 사용자의 명시적 허가 없이 수행하지 않는다.

## 8. Git·브랜치·복구·배포

- **브랜치 전략:** 안정적인 `main` + 기능별 작업 브랜치. 브랜치 생성·전환 등 작업에 영향이 있는 Git 조작은 계획에 포함해 승인받는다.
- **커밋:** 구현·검증·완료 보고 후 사용자 승인받고 생성한다. 임의 커밋 금지.
- **push:** GitHub로 전송하기 전 별도 명시적 승인 필수. 커밋 승인이 push 승인을 뜻하지 않는다.
- **복구·되돌리기:** 대상, 영향, 데이터 위험, 복구 방법을 설명하고 승인받은 뒤 수행한다. `reset --hard`, 강제 push, 기록 재작성 등 파괴적 작업은 임의 실행하지 않는다.
- **배포:** 배포 대상, 변경 사항, 테스트 결과, 위험과 복구 계획을 보고하고 승인받은 뒤 실행한다. GitHub push와 실제 서비스 배포는 별도 승인이다.
- Git 기록이나 배포 자동화가 존재하더라도 사용자 승인 원칙을 우회하지 않는다.

## 9. DB·보안·개인정보

- DB 스키마·컬럼·제약조건·인덱스·정책·데이터 변경 전 **변경 계획, 기존 데이터 및 기능 영향, 위험**을 보고하고 승인받는다.
- DB 변경은 **버전 관리되는 마이그레이션 파일**로 기록한다. 마이그레이션 파일 작성과 적용 범위를 계획에 명시하고, 적용 전 승인받는다.
- **개발 DB와 운영 DB는 별도 Supabase 프로젝트**로 완전히 분리한다. 개발·테스트는 개발 DB에서 수행한다.
- 운영 DB 접근·마이그레이션·데이터 수정·삭제는 **운영 대상임을 명시한 별도 승인**을 받는다. 적용 전 백업·복구 가능성을 확인한다.
- **최소 권한 원칙**과 Supabase **RLS(Row Level Security, 행 단위 접근 제어)**를 엄격히 적용한다. 관리자 권한은 신뢰할 수 있는 서버 측에서 검증하며, 클라이언트 표시 여부만으로 권한을 판단하지 않는다.
- 공개 조회·회원 리뷰·관리자 전용 사진 업로드·비회원 제보·관리자 수정의 구체적인 권한은 `DB.md`와 승인된 요구사항을 따른다.
- 외부 입력은 검증하고, 인증·권한 검사 및 비회원 제보의 남용 방지 등 `DB.md`의 보안 조건을 지킨다.
- 비밀번호, 토큰, API 키, 개인식별 정보 등 민감한 값은 로그·오류 메시지·커밋에 기록하지 않는다.
- 보안 위험·데이터 손상 징후를 발견하면 **위험 작업을 중단하고 안전한 진단과 보고만 수행**한다. 무단 수정·삭제·차단·복구는 긴급 시에도 금지한다.

## 10. 오류 처리·외부 API 장애

- 사용자에게 기술적 스택 트레이스 대신 **이해하기 쉬운 오류 설명과 가능한 해결 행동**을 안내한다.
- 로그는 진단에 필요한 오류 종류·발생 위치·시각 등 최소 정보만 기록하며 비밀정보·개인정보를 제외한다.
- 네이버 지도 또는 Supabase 등 외부 서비스 장애 시 **영향받는 관련 기능을 중단하고 장애를 명확히 안내**한다. 장애 중인 기능을 정상처럼 표시하지 않는다.
- **자동 재시도는 하지 않는다.** 사용자가 직접 재시도할 수 있는 방법을 제공한다. 제출 중복 등 부작용에 주의한다.
- 예상하지 못한 오류를 발견하면 원인·영향·수정안을 보고하고 승인 대기한다. 사소한 오류라는 이유로 임의 수정하지 않는다.
- 영업정보의 확인 여부를 알 수 없으면 **확인된 영업 중 상태로 표시하지 않는다**.

## 11. 성능·접근성·화면 크기

- 지도 이동, 검색, 시간 필터, 장소 목록 등 **핵심 사용자 경험의 반응성**을 우선한다. 불필요한 복잡한 최적화는 하지 않는다.
- 로딩, 빈 결과, 실패 상태를 명확히 구분한다. 상황에 맞는 로딩 표시·스켈레톤·안내를 제공한다.
- 웹 접근성은 **WCAG 2.2 AA 수준을 목표**로 한다. 키보드 조작, 포커스, 명확한 이름, 색상 대비, 보조기술 접근성을 고려하고 미충족 항목은 보고한다.
- 1차는 **데스크톱 전용**으로 구현한다. 모바일 화면에는 지원 안내를 표시한다. 모바일 전용 기능·반응형 전체 구현은 별도 승인 전 금지한다.
- 성능 문제가 발견되면 측정 결과·원인·개선안·영향 범위를 보고하고 승인받은 뒤 최적화한다. 성능을 이유로 디자인이나 기능을 임의 변경하지 않는다.

## 12. 명령어 실행 권한

### 별도 추가 승인 없이 허용되는 비파괴적 작업

- 파일·폴더·Git 상태 **조회**, 문서·코드 **검색**, 설정·로그의 안전한 **읽기**.
- **이미 승인된 작업 범위의 테스트·타입 검사·린트·빌드** 실행. 단, 실행 시 파일·DB·외부 서비스에 실질적 변경이 발생하는 명령은 승인 대상이다.
- 변경을 수반하지 않는 원인 분석과 영향 검토.

### 반드시 사전 승인받아야 하는 작업

- 코드·문서·설정 파일의 생성·수정(현재 승인된 단계 범위에 포함되지 않은 경우).
- 리팩터링, 파일·데이터 삭제, 패키지·도구 설치·업그레이드.
- DB 마이그레이션 적용, DB 데이터 변경, 권한·보안 정책 변경.
- Git 커밋·push·되돌리기·강제 조작, 외부 저장소 업로드.
- 배포, 외부 계정·서비스 설정 변경, 운영 환경에 영향을 주는 조치.
- 승인 범위를 벗어나는 모든 명령과 작업.

**주의:** 터미널 명령이 단순해 보이더라도 부작용이 있다면 실행 전에 승인받는다. 허용된 조회·검사는 사용자의 비밀정보를 출력하거나 외부로 전송할 권한을 뜻하지 않는다.

## 최종 검토 Q1–Q8 확정 사항 (2026-11-05)

> 이 절은 사용자 승인으로 확정된 최신 정책이다. 같은 문서 또는 다른 문서의 이전 **잠정/권장/확인 필요** 문구와 충돌하면 이 절을 우선 적용한다. 단, 구현상 추가 확인이 필요한 외부 API 제약은 검증한다.

1. **장소 상세:** 대표 사진이 있으면 뒤로가기 다음의 최상단 사진 헤더로 표시한다. 사진이 없으면 영역을 생략한다. 장소명과 선택 시간 영업 상태를 이어서 표시한다. 주간 영업시간은 기본 접힘, 사용자 조작으로 7일 시간표를 펼친다. 적용되는 특별 영업/임시 휴무 등 예외는 접힘 상태에서도 상단에 안내하고 실제 영업 판정에 반영한다.
2. **지도와 필터:** 지도 이동만으로는 재검색하지 않는다. '이 지역 검색'을 눌렀을 때 검색 영역을 변경한다. 지도만 이동한 상태에서 카테고리/태그/시간 필터를 변경해도 **마지막으로 확정된 검색 영역**을 대상으로 검색한다. 카테고리/태그는 변경 즉시 검색한다. 시간 슬라이더는 드래그 중 선택 시각 표시만 갱신하고, 놓았을 때 서버에 검색 요청한다.
3. **검색 결과 그룹 및 정렬:** `full`(전체 영업) → `partial`(일부 영업) → `unknown`(영업정보 미확인) → `closed`(선택 시간에 영업하지 않음) 순으로 **모든 그룹을 표시**한다. `full`은 확정 검색 지도 중심과의 거리순, `partial`은 선택 구간 중 실제 영업 시간의 총 길이 내림차순 후 거리순, `unknown`은 하단 별도 그룹, `closed`는 최하단 별도 그룹이다. 동일 조건의 안정적 정렬을 위해 ID 등 결정적 타이브레이커를 사용한다. 미확인 장소를 영업 중이라고 단정하지 않는다.
4. **정보 신뢰도:** 마지막 관리자 실확인 시각으로부터 **30일 초과** 시 '정보 오래됨' 경고를 표시하되 원래 그룹과 정렬은 유지한다. '영업하지 않음' 이용자 제보가 접수되면 관리자 확인 전에도 '영업 여부 제보 있음' 경고를 표시하고 기존 영업시간 판정은 유지한다. **확인일은 관리자가 실제 영업정보를 확인했을 때만** 갱신하며, 단순 제보 접수나 데이터 수정만으로 갱신하지 않는다.
5. **콘텐츠 운영:** 회원 텍스트 후기(별점/후기 사진 없음)는 작성 즉시 공개하며 신고 후 관리자 검토한다. 장소 대표 사진의 등록/변경은 관리자만 할 수 있다. 장소 신규 등록/정보 수정 제보는 승인 전 실제 장소 데이터에 반영하지 않으며, 제출자에게 접수 안내를 제공하고 **회원에게는 본인 제보의 검토 상태 조회**를 제공한다. 비회원 제보도 기존 허용 원칙을 유지하되 계정 없는 제보자에게 회원용 조회 기능을 약속하지 않는다.
6. **시간 검색:** 시작 날짜만 선택하며 종료 날짜는 자정 통과에 따라 자동 계산한다. 슬라이더 범위는 **18:00~다음 날 07:00**, 30분 단위이다. **특정 시각과 시간 구간** 검색을 모두 지원한다. 미래 날짜 검색 상한은 두지 않으며, 반복 영업시간과 등록된 날짜별 예외로 계산한다. 미등록 미래 예외는 보장하지 않는다고 안내한다. '지금' 기본값이 30분 격자와 맞지 않을 경우 실제 현재 시각을 유지할지 스냅할지는 구현 전 별도 확인이 필요하다.
7. **기술 스택:** **Next.js + TypeScript**, **Cloudflare 배포**, **네이버 지도 API**, **Supabase PostgreSQL + PostGIS / Auth / Storage** 확정. Next.js의 Cloudflare 런타임/배포 어댑터 호환성, 네이버 지도 다크 테마 지원 여부는 구현 전 기술 검증한다. 검증 없이 프레임워크를 임의 변경하지 않는다.
8. **초기 데이터:** 직접 검증한 실제 장소 **30개**를 최초 공개 목표로 한다.

**DB/API 주의:** 이전 검색 응답의 `coverageStatus: full|partial|unknown`은 `closed`를 포함하도록 확장해야 한다. 부분 영업시간의 정렬값(선택 구간과 실제 영업 구간의 교집합 총 분)을 계산·반환 또는 서버 내부 정렬 키로 사용한다. `unknown`과 `closed`는 별도 상태이며 혼합하지 않는다. 페이지네이션은 그룹·정렬 순서를 유지해야 한다.
